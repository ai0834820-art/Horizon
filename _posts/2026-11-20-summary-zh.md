### [PostgreSQL 19 发布：WAIT FOR LSN 支持备库读己之写](https://simonwillison.net/2026/Nov/19/postgresql-19/) ⭐️ 8.0/10

PostgreSQL 19 已发布，比通常的 9 月发布窗口晚了约两个月；Simon Willison 引述的博客将延迟主要归因于团队需处理大量由 AI 报告的漏洞。此次更新面向将读请求发送到备库的应用，新增 WAIT FOR LSN 命令：备库会话可等待 WAL 回放到指定 LSN 后再执行查询，从而读到刚在主库写入的数据。典型流程是先执行 pg\_current\_wal\_insert\_lsn\(\) 取得类似 0/0306EE20 的 LSN 并保存，后续请求在备库执行 WAIT FOR LSN &\#x27;0/0306EE20&\#x27; WITH \(TIMEOUT &\#x27;0.1s&\#x27;\)。超时参数可选；若设置超时且备库未在期限内追上，语句会报错。

rss · Simon Willison · 11月19日 20:43

**「背景」** PostgreSQL 的流复制备库通过持续回放主库产生的 WAL 来保持同步，而 LSN 用于标识 WAL 中的具体位置；备库在某一时刻可能尚未追平主库，因此直接读取备库会看不到刚提交的写入。该文将 PostgreSQL 19 较往年惯例推迟约两个月发布，主要归因于团队需要处理一批由 AI 报告的漏洞。

**「影响」** 对运行主备复制的团队，这提供了一种数据库层面的按请求一致性机制：应用可继续把读流量放在备库，同时通过传递最近写入的 LSN 避免紧随写入后的读请求读到旧数据。代价是应用需自行保存并传递 LSN，并为 WAIT FOR LSN 设置合理的超时与错误回退策略。

### [PHP 修复大小写 scheme 导致 HTTPS 静默降级明文的漏洞](https://x.com/ljachowicz/status/2123477025268924514) ⭐️ 8.0/10

PHP 的 HTTP/FTP 流包装器在识别 scheme 时不分大小写，但只有第五个字符是小写 s 时才启用 TLS，因此 HTTPS://、httpS://、FTPS:// 这类写法会被当作明文 HTTP/FTP 发出，Basic 认证头、令牌、Cookie、POST 请求体和 FTP 登录信息随之以明文暴露，即使是被第三方重定向到这种地址也同样受影响。据提交者 Lukasz Jachowicz 称，该缺陷已存在约 20 年而未被发现。漏洞编号 CVE-2026-128064（GHSA-f6gg-rchx-xw8j），CVSS 4.0 评分 8.2，已在 PHP 8.2.36、8.3.37、8.4.28、8.5.13 和 8.6.0 中修复。8.1 及更早分支已 EOL，不会获得修复，用户只能自行将 URL 的 scheme 统一转为小写。

telegram · zaihuapd · 11月20日 03:04

**「背景」** PHP 的 HTTP/FTP 流包装器是 \`file\_get\_contents\`、\`fopen\`、\`copy\` 等函数打开远程 URL 的底层机制，URL 的 scheme 决定调用哪个协议处理器以及是否启用 TLS。该机制长期按大小写不敏感方式匹配 scheme，因此 \`HTTPS://\` 与 \`https://\` 会被视为同一种协议，但 TLS 开关的判断并未同步做到大小写无关。

**「影响与应对」** 任何接受外部或用户提供 URL 的代码路径——重定向跟随、回调地址、配置文件——都可能在没有任何报错或日志异常的情况下失去传输加密，因此受影响系统仅靠监控难以发现。无法升级到修复版本的用户应在把 URL 交给流包装器之前统一规范化 scheme 为小写。

### [Hacker News 帖称 Gemini 4 Neon 登顶 Models Engineering Index](https://git-aarvin.github.io/mei/) ⭐️ 7.0/10

Hacker News 上的一篇帖子声称，Gemini 4 Neon 已在 Models Engineering Index 上排名第一；但所给材料没有官方模型公告、评测方法或独立复现，因此这一“第一”目前只能视为未经核实的说法。评论者称，Neon 在编码任务上大致相当于 Opus 5.5/Fable，并且在大型 monorepo 的长时语言移植工作中，“high”档比 Opus 5.5 的“medium”档更快、更便宜，结果相近。也有评论者指出，实际获取和使用 Neon 的成本不低，部分讨论者可能尚未亲自使用过该模型。

hackernews · hn-aarvin · 11月19日 23:35 · [社区讨论](https://news.ycombinator.com/item?id=50568130)

**「背景」** 谷歌的发布说明将 Gemini 4 Neon 定位为面向复杂软件工程与生产级工作流的模型：Carbon 负责最难的长周期项目，Hydrogen 负责快速日常执行，Neon 则在深度与效率之间取平衡；官方标价为每百万输入 token 3 美元、缓存输入 0.15 美元。该模型已通过 Gemini API 提供，此次引发讨论的 Models Engineering Index 排名就出现在这一新模型发布之后。

**「对模型选型的实际影响」** 对正在挑选编码模型的开发团队来说，评论中的实际使用报告比榜单名次更有参考价值：有用户称 Neon 的 “high” 档在大型 monorepo 的长时间语言迁移任务上，结果与 Opus 5.5 “medium” 相近，但速度更快、成本更低，该用户已把两处工作区都改用 Neon；另一名用户也认为其编码水平与 Opus 5.5 大致相当。由于“第一”只来自一个个人维护的细分指数，且现有材料未给出评测方法，团队在替换现有模型前，应在自己的代码库和提示设置上复现这一对比。

**「社区讨论」** 评论区的分歧主要在于证据强度：有用户认为不少发言者并未真正使用 Neon，且获取访问权限既困难又昂贵；同时也有自称使用过的用户报告称，Neon 在编码、文档和长时任务上接近 Opus 5.5/Fable，速度和成本更优。另有用户称，在 3D 游戏地图生成中 Neon 的表现与 Opus 相当，而 GPT 模型（包括刚发布的 6.2 Astra）需要额外提示才能达到类似效果。

### [OpenJDK 疑似 Java RCE 漏洞披露引发争议](https://github.com/openjdk/jdk/pull/32781) ⭐️ 7.0/10

OpenJDK 的拉取请求 \#32781 涉及一个疑似 Java 远程代码执行漏洞；Hacker News 上的讨论集中在 Oracle 如何处理披露，以及 LLM 辅助研究是否独立发现了该问题。评论区引用 Adoptium 支持议题 \#1480 称，PR 作者曾在 10 月 1 日表示收到 Oracle 邮件，要求其在获批前不要推进 PR，10 月 28 日又称该事项“已被 Oracle 接管”。另有评论称，Oracle 在合并提交中的说明与 PR 中的表述逐字相同。上述说法均来自评论者，所给材料未确认漏洞严重性、受影响版本或利用细节。

**「背景：Java 4 Shell 是什么」** “Java 4 Shell”得名于 2021 年的 Log4Shell 漏洞，编号为 CVE-2026-114938；据 Calif 称，这是 OpenJDK Base64 解码器中的一处内存破坏漏洞（memory-corruption），由该公司发现并报告。该漏洞可让未认证攻击者远程执行代码，据报受影响的应用包括 Jenkins、Atlassian Jira、Confluence 和 Keycloak 等企业级 Java 应用。本次讨论所围绕的 OpenJDK 拉取请求，即针对这一问题的提交。
