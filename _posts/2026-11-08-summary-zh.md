### [报告称 Claude Code 本地设置泄露 1,122 个公开文件中的密钥](https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again) ⭐️ 7.0/10

一份安全报告称，公开 GitHub 仓库中有 1,122 个文件因提交 Claude Code 的 .claude/settings.local.json 而暴露了密码或密钥；问题并非按下“Don&\#x27;t Ask Again”本身，而是用户把包含已批准命令的本地设置一并提交，且这些命令中直接写有凭据。Claude Code 团队工程师 Boris 在 Hacker News 上表示，该文件本应只保留在本地，Claude 创建时会自动将其加入 .gitignore，这些案例属于手动创建并提交；他同时承认 Claude Code 过去没有做密钥清理，正在研究预防措施。

hackernews · shmulc · 11月7日 20:45 · [社区讨论](https://news.ycombinator.com/item?id=50407882)

**「权限设置如何写入本地文件」** Claude Code 通过分层的 settings.json 管理命令权限，allow、ask、deny 三档分别对应自动放行、逐次询问和禁止执行。用户选择“Don&\#x27;t Ask Again”后，被批准的命令文本会写入项目级 .claude/settings.local.json，后续会话可直接复用。Claude Code 团队说明该文件设计为仅本地保留，由 Claude 创建时会自动加入 .gitignore，手动创建的文件则不会获得这层保护。

**「提交前检查本地设置文件」** 对使用 Claude Code 的开发者而言，直接后果是：一旦包含已批准命令和明文密钥的 \`.claude/settings.local.json\` 被提交并推送，任何能读取该仓库的人都能拿到这些凭据；Claude Code 自己写入该文件时会将其加入 gitignore，但手动创建或复制进来的文件不受此保护，因此需要在提交前检查并移除它，或改为让命令从外部凭据存储读取密钥而非把密钥写进命令行。外部扫描也显示这类配置中确实存在有效凭据：一项 2026 年 4 月的研究称，在 428 个含该文件的 npm 包中有 33 个包含仍然有效的 Anthropic 凭据。

**「社区讨论」** 有评论者批评标题误导，强调风险成立需要同时提交本地设置并在已批准命令中写入密钥；也有开发者分享更严格的权限隔离做法，例如为每个任务使用隔离网络中的临时虚拟机并配合 API 代理，或让 Claude 通过 1Password CLI 按需取用凭据。Boris 表示正在研究预防措施，但未说明具体改动或时间表。

### [用 10 美元 OpenStick 搭建自托管 homelab](https://blog.bosscher.ch/posts/openstick/) ⭐️ 7.0/10

一篇个人博客文章介绍了作者如何在售价约 10 美元的 OpenStick USB 设备上运行自托管 homelab；作者称，只要选对软件，这块廉价硬件就能承载不少服务。文章把它作为内存价格高企时低成本入门自托管的方案，属于个人实践而非独立性能测试。评论者还询问 OpenStick 的购买渠道，并把它与 Raspberry Pi Zero/Zero 2 作比较。

hackernews · LaurensBER · 11月7日 18:12 · [社区讨论](https://news.ycombinator.com/item?id=50406670)

**「背景」** OpenStick 是一款售价约 10 美元、以 USB 形态提供的小型计算设备，通常运行嵌入式 Linux。把这类设备当作 homelab 服务器时，可用内存和处理器性能会直接限制能运行的服务数量，因此选择轻量软件很关键。

**「实际影响」** 对打算复现的读者来说，真正的门槛在于硬件改造，而非购买：OpenStick 需要按社区方案将 Qualcomm MSM8916 4G LTE USB 上网卡（如 UZ801、UFI003）刷成 Debian，才能当作服务器使用；512 MB 内存只够运行经过挑选的轻量服务，作者的广告拦截、监控和少量自托管应用可以跑起来，但一旦增加负载或考虑组集群，就必须先确认供电、网络连接和镜像兼容性。

**「社区讨论」** 有评论者认为 OpenStick 比其集群中使用的 Raspberry Pi Zero 更强、性能大致相当于 Zero 2，并希望出现可直接插入带 PoE 的以太网交换机、像插节点一样组建集群的棒状设备。也有人讨论 Fusion 与更轻量的 miniflux/picoflux 之间的取舍，并强调低内存设备需要挑选高效的软件。

### [Coldframe：单文件 Python 冷柜控制器蜜罐](https://github.com/hedgerow-dev/coldframe) ⭐️ 7.0/10

安全研究者发布 Coldframe：一个单文件、仅使用 Python 标准库实现的蜜罐，用来伪装成超市制冷控制器。它分别模仿 Danfoss AK-SM 800A 与 Dixell XWEB 的界面和响应特征，作者称其在 Shodan 上会被识别为真实设备，而非蜜罐。除记录 CVE-2025-41450 的利用尝试并判断当日“code of the day”是否正确外，它还会标记针对另外三个 Danfoss CVE 和 XWEB 漏洞的探测；使用默认口令可进入一个带除霜按钮的假门店仪表盘，以便观察登录后的后续行为。作者表示目前只有两个实例上线一天，迄今仅看到通用扫描器和 Shodan 爬虫 refrigerator.census.shodan.io 的访问。

hackernews · hedgerow-dev · 11月7日 17:27 · [社区讨论](https://news.ycombinator.com/item?id=50406292)

**「背景」** 工业控制系统蜜罐会把自身伪装成真实可访问的设备，在记录探测与利用尝试的同时不连接任何实际控制逻辑。超市制冷控制器属于常被 Shodan 等搜索引擎索引的联网 OT 设备，因此常被用作此类诱饵的仿冒对象。

**「影响」** 对 ICS/OT 研究者和暴露设备运营方而言，Coldframe 能以很低依赖搭建可交互诱饵，观察攻击者登录后如何操作，而不只捕获首轮扫描；但它本身不是修复或防护措施，且公开观测仅来自两个实例上线一天，尚不足以量化真实攻击面。

**「社区讨论」** 评论区中，supriyo-biswas 质疑仅依据 Shodan 记录复刻设备的可靠性，认为许多在线设备本身可能是蜜罐或已被入侵，建议用实体漏洞设备验证；xrd 则追问所谓大规模冷柜被黑是否有定论，而非只是同一时间软件更新造成的假象。作者回应称超市通常没有安全团队，补丁、VPN 和强密码应默认由厂商或安装商提供。

### [MaxxBench 检验 DeepSWE 分数是否经得起任务规格改动](https://maxxbench.unlap.ai/research/why-maxxbench/) ⭐️ 7.0/10

MaxxBench 的一项分析考察 DeepSWE 基准分数在任务说明发生变化后是否仍然成立，而不只是复述原始榜单分数。该分析把讨论引向 LLM 评测的有效性：一个分数究竟代表可泛化的模型能力，还是对特定任务表述的适应。现有材料没有给出具体分数变化幅度或任务规格改动清单，因此效应大小仍不明确。

hackernews · antiuniverse · 11月7日 17:19 · [社区讨论](https://news.ycombinator.com/item?id=50406222)

**「背景」** DeepSWE 是一个包含 113 个原创、长周期软件工程任务的基准，其设计动机之一是避免从公开 GitHub 合并修复中出题造成的预训练污染——否则高分可能反映记忆而非解题能力。MaxxBench 则选取其中 89 个 DeepSWE 任务，通过改动指令或起始代码，观察模型表现对任务表述变化的敏感度。这两点构成了理解 MaxxBench 为何质疑“DeepSWE 分数是否稳健”的前提。

**「影响」** 对依赖 DeepSWE 选型或汇报模型能力的人而言，单一分数不足以说明模型在任务描述稍变时仍可靠；更稳妥的做法是查看基准对任务规格扰动的敏感性，并核查基准自身 bug 是否会影响结果。

**「社区讨论」** 评论者认可用“改动一个参数再看分数”来检验基准泛化性，并指出讨论中的图表显示较小模型（名称含“-flash”者以及 OpenAI Luna）分数下滑最明显。另一些评论者把问题归因于训练和评测环境未充分变化，而非实验室直接针对基准训练，同时提醒 DeepSWE 存在 bug，这些都只是社区判断。

一篇技术调查文章称，macOS 中存在未公开的 Apple Intelligence 相关组件：一对后台守护进程会构建关于用户本人、联系人、人物关系、通信对象和位置信息的个人知识图谱，并据此推断亲属等关系。文章称这类组件自 2022 年起随每台 Mac 提供，但未见于公开文档；作者还发布了后续研究。上述说法来自文章及其作者，尚非 Apple 的公开确认或独立复核。

### [Claude Code 被指将登录邮箱注入联网请求](https://github.com/anthropics/claude-code/issues/107757) ⭐️ 7.0/10

有开发者投诉称，Claude Code 会把用户的登录邮箱填入联网请求并发送，导致其每天收到大量诈骗邮件。Anthropic 工程师表示，此前为了解决模型乱填作者名的问题，登录邮箱被放入了模型上下文。该问题据称今年 7 月已有人报告，邮箱被发送至 Wikipedia、美国证券交易委员会等目的地。2.1.317 版已加入拦截，但据称可被 Python 脚本绕过，公司仅承诺在下一版本中从上下文移除登录邮箱。

telegram · zaihuapd · 11月7日 08:09

**「背景」** User-Agent 是 HTTP 请求中用于标识客户端的一段头信息；工具结果中的缺陷报告称，Claude Code 会在执行网页搜索时把用户登录邮箱写进该请求头，目标站点因而能直接读取。另一份技术分析称，该值来自 \`CLAUDE\_USER\_EMAIL\` 环境变量，缺失时会回退到 git 配置，这也解释了邮箱为何会随不同本地环境进入请求。

**「影响与应对」** 使用 Claude Code 联网搜索的用户仍可能把登录邮箱通过 HTTP User-Agent 等请求头发给第三方站点；2.1.317 版加入的拦截可被 Python 脚本绕过，因此在下一版本真正移除上下文中的登录邮箱之前，升级到 2.1.317 并不足以完全阻断泄露。对隐私敏感的用户应避免用常用个人邮箱账号登录，或在修复发布前限制 Claude Code 的联网抓取行为。

### [GitHub Rubicon 架构瞄准 AI 智能体高并发](https://github.blog/engineering/architecture-optimization/inside-githubs-new-git-storage-architecture/) ⭐️ 7.0/10

GitHub 公布代号 Rubicon 的新 Git 存储架构，目标场景是大量 AI 智能体同时操作同一个仓库。GitHub 称内部测试中该架构支持 5,000 个智能体协作、每秒处理 7,200 次推送，并保持较低读取延迟；这些是厂商内部测试数据，尚未独立验证。该架构将 Git 对象存入 Azure Blob Storage，由 Ref-CAS 管理引用状态，虚拟副本处理读写、后台节点压缩数据包；目前仅处于有限私有预览，GitHub 表示将逐步扩大范围。

telegram · zaihuapd · 11月7日 14:12

**「背景」** GitHub 旧版 Git 存储架构 Spokes 通过三阶段提交协调写入；外部报道将其作为 Rubicon 的对照基线，称新架构写入吞吐最高提升 35 倍。Rubicon 的关键设计是把不可变 Git 对象与可变引用拆开，只对引用更新保留严格的排序要求。

**「影响」** 对需要让多个智能体并行读写同一仓库的团队而言，在 Rubicon 仍处于有限私有预览、尚未普遍开放期间，不能依赖这一吞吐能力，仍需按现有 GitHub 服务的限制设计智能体并发工作流。
